## Files and ownership

- `account-service/worker.mjs`: portal response, API authorization, registration, sessions, recovery, private workspace writes, counters, referrals, downloads and retention cleanup.
- `account-service/crypto.mjs`: version 1 password verification, random values, hashes, keyed hashes and native constant-time comparison.
- `account-service/limits.mjs`: shared policy and Europe/Athens day boundaries. The public pure workspace engine in `assets/account-core.js` matches these limits.
- `account-service/migrations/`: D1 tables, constraints, capacity/quota triggers and private account records. Apply each migration once, in order, only to the Test database.
- `account-service/sponsor-catalogue.mjs`: AES-256-GCM encrypted script bytes with IDs, language names, versions and SHA-256 metadata. There are no plaintext scripts or keys here.
- `assets/account-live.js`: authenticated portal, browser password derivation, serialized syncing, recovery-code download, verification request and reward updates. `account-template.js` retains the workspace UI and an explicit memory-only local/static preview. `account-config.js` stays disconnected on the static site; the Worker injects the live configuration.
- `scripts/package_sponsors.py`: owner-controlled packaging. It requires Python `cryptography`; normal site builds do not. Plaintext sources, manifest and 32-byte hexadecimal key file must be outside the repository; Unix key permissions must be 0600. The manifest lists `id`, `source`, `filename`, `language` and bilingual `description`. Filenames end in `(English).py` or `(Ελληνικά).py`. The output is the ciphertext catalogue, not a secret file.

## Limits and privacy

There are at most 300 existing accounts and 444 unique authenticated accounts per Athens calendar day, rather than concurrent sessions. Authenticated requests record daily activity; deletion removes the account's records. The SQL constraints enforce caps even if clients lie or submit concurrently. Counters show unknown when disconnected; the preview never increments them.

Logical notes storage is 400,000,000 bytes overall, 900,000 bytes per account (decimal units), including UTF-8 file/folder paths. The 300 personal ceilings total 270,000,000 bytes; the overall ceiling remains 400,000,000 bytes. Database indexes, SQLite overhead, credentials and recovery history are additional physical storage; these figures do not promise that arbitrary activity fits every Cloudflare quota. There are at most 200 TXT files, 50 folders and eight path components. Reject unsafe/reserved paths, case-folded duplicates, missing parents, non-UTF-8 imports, NUL and non-text controls. JSON writes are bounded to 1,900,000 encoded bytes. Export one TXT directly; export multiple items or any folder as a ZIP with paths and empty folders.

D1 contains profile name, email, date of birth and age at registration, protected verifier, private notes, pins, consent version/timestamp, sessions and referral state. Passwords, session cookies, recovery codes and notes are never placed in public GitHub, search catalogues, LLM exports or localStorage. Notes are private application data, not end-to-end encrypted data inaccessible to the database operator. Do not back up personal data into public or private GitHub repositories as plaintext name files. Users export their own TXT/ZIP backup. Account deletion cascades through application tables; Cloudflare recovery backups have their own retention policy.

The application uses keyed network hashes, grouping IPv6 at /64, instead of storing raw IPs. Signup-network signals have rolling 30-day retention, refreshed on profile access; hourly cleanup expires them, old daily activity, sessions, verification tokens and rate-limit records. Cloudflare itself may process operational security logs. Turnstile is restricted to the Test Worker hostname and expected registration/login/recovery action. The Worker does not log credentials or notes.

## Authentication and concurrent edits

A password of 12–128 characters is checked in the browser. The browser derives a 256-bit credential using PBKDF2-SHA256 with 600,000 iterations and the versioned account salt. The server applies another PBKDF2-SHA256 operation with a random per-account salt and 100,000 iterations, then an HMAC using the server-only password pepper. The client-derived credential is password-equivalent: transmit only over HTTPS and never persist or log it. A live runtime probe confirmed that this Worker rejects a single PBKDF2 call above 100,000 iterations; do not silently lower the browser's 600,000 iterations. This layered design is tested here; it is not a claim of an independent cryptographic audit.

Sessions use random 256-bit tokens, store only token hashes and expire after seven days. Cookies use Secure, HttpOnly, SameSite=Lax and the `__Host-` prefix. Mutations require exact Origin, JSON and the session CSRF token. There is no client-supplied user-ID authorization. Recovery uses a separately hashed 256-bit code shown once after registration/recovery; successful recovery rotates it and revokes prior sessions. Login and recovery are rate limited by keyed account/network identifiers. Email repetition catches typing mistakes; it does not verify ownership.

Workspace operations serialize snapshots with an expected revision. One atomic D1 batch claims a random write token, deletes this account's previous rows and inserts the validated snapshot. A stale revision changes no rows and returns 409. Quota failures roll back the batch. The client keeps its local copy, stops conflicting writes and asks for export before reload. It does not silently overwrite another tab's newer notes. A failed sign-out sync keeps the account open. The unload warning covers unsaved editor text and unsynced changes.

## Referral and email gate

Rewards require the inviter's verified email and three additional qualified invitees per script: 3 unlock the first, 6 the second, 9 the third. Each download rechecks eligibility. Each invitee needs a distinct verified identity, a separate signup network, at least 24 hours since referral creation and activity on two Athens dates. Gmail/Googlemail dots and plus aliases normalize to one identity. Shared networks and reused referral networks do not qualify; this conservative policy can reject genuine household friends. IPs, email and Turnstile cannot prove three unique humans. Pending referrals expire after 30 days; both accounts need retained network signals. Deletion or invalidation can remove eligibility.

The adapter `account-service/mail.mjs` supports Brevo (`MAIL_PROVIDER=brevo`) and Resend (compatibility default). It reads `MAIL_API_KEY` or the fallback `DedSec-Project-Email`, plus `MAIL_FROM`. Verification uses `/verify?token=…` on the account Worker, with a hashed single-use token expiring after one hour. It confirms the bound account without an existing session, displays success and redirects to the selected website homepage. Missing configuration returns `email_not_configured`; configured bindings do not prove delivery. The authenticated `verify/confirm` API remains for legacy clients. Email 2FA, passkeys and two-address email changes are described in chapter 23. No newsletter or sponsor email is sent.

Cloudflare outbound email to arbitrary recipients requires Workers Paid, so it was not enabled. Keep Workers Free; reaching free request/read/write/storage limits can interrupt service. Connecting Cloudflare is not a promise of unlimited capacity. The sender provider must also stay within its free plan. The application caps verification sends at 100 per UTC day and 3,000 per calendar month; the provider may have less remaining quota when used by other applications. This can defer verification during a registration burst. The outstanding sender connection is a deployment prerequisite for public referral testing, not a UI-only detail.

## Script release updates and boundaries

The four rewards are Face Detector and Steganography, each in English and Greek. Original uploads remain outside the public repository. Prepared Face Detector copies reject path traversal, malformed PNG/WebM payloads and oversized uploads, generate unique capture filenames, and bound capture storage. Prepared Steganography copies write salted PBKDF2-SHA256/600000 Fernet payloads and can still read legacy unsalted payloads. Camera, network tunnel, dependency installer and Android UI were not executed during the focused source audit; do not call the tools universally safe or platform-certified.

AES-GCM authenticates each script's ID, filename and plaintext digest. The AES key exists as `SPONSOR_KEY`, outside GitHub, browser code and public assets. The Worker checks session and current eligibility on every download, then decrypts and verifies SHA-256. Authenticated HEAD requests perform the same server-side verification but return only headers, including the computed digest, and no plaintext body. The browser independently verifies the same digest before saving. Public ciphertext is discoverable; it is not readable without the key. An authorized recipient can redistribute a downloaded plaintext file, which encryption cannot prevent.

For updates, package new source bytes with a fresh release version and owner-held key, upload the matching catalogue/code and `SPONSOR_KEY` together in one Worker version, and deploy that version. Preserve/inherit all other secret bindings. Never rotate `HMAC_SECRET` or `PASSWORD_PEPPER` casually: existing salts, identities and verifiers depend on them. Keep previous Worker versions for rollback. Existing users fetch the latest catalogue at sign-in, on manual refresh, and every 15 minutes while the profile is visible; they do not receive stale account-specific script copies. Updating the repository alone does not deploy the Worker.

## Schema version 3: capacity and date of birth

`0003_account_capacity_and_birth.sql` replaces only the policy singleton and recreates its four dependent triggers, lowering existing-account capacity to 300. It preserves daily 444 and storage policy, profiles, credentials, notes and their usage counter. Historical 0001/0002 remain unchanged. It adds `date_of_birth` as calendar-validated ISO `YYYY-MM-DD`, with an insert trigger requiring it for new users. Legacy rows retain NULL rather than an invented birthday. `account_schema_migrations` records versions 1–3; this is independent of Wrangler's migration ledger. The migration is not idempotent: inspect the ledger/schema before executing, and inspect again after an uncertain network response instead of retrying blindly.

Registration requires both age and birth date. The server rejects malformed dates, invalid leap days, future dates, ages outside the current 18–130 range (migration 0004 supersedes the original constraint) and an age inconsistent with the birth date at today's Europe/Athens date. On a leap-day birthday, the age increments on March 1 in non-leap years. `age_at_registration` is a historical snapshot, not a live age field; the authenticated profile response labels it `ageAtRegistration` and returns `dateOfBirth` only to its owner. Public status, referral invitations and download metadata contain no birth dates. DOB is self-reported, not identity verification or a child-consent system. Terms/privacy version is `2026-10-21-v3` and both public language forms disclose collection before acceptance.

Migrate while registration is disabled. Existing Worker versions with positional eight-column user inserts cannot register against the nine-column schema. Deploy this version's explicit-column inserts with the migration; a safe rollback disables accounts or keeps a schema-compatible registration handler. Keep the new column and data during code rollback. See chapter 09 for clean-install versus already-initialized D1 instructions.

## API contract and data ownership

All paths below are relative to `/api/account/`. Mutations require exact Origin and JSON; authenticated mutations additionally require the current CSRF token. Error JSON uses `error`; never parse raw exception text in the UI. Private responses use no-store. There is no public user directory or arbitrary user-ID lookup.

| Method/path | Input and result | Authorization |
|---|---|---|
| GET `status` | Real counts, limits, service/mail readiness and terms version | Public; no user fields |
| POST `challenge` | Email → versioned client salt/derivation contract | Rate limited; no password |
| POST `register` | Names, repeated email, age, dateOfBirth, prehash, terms and CAPTCHA → recovery code/session | Turnstile register action, SQL capacity/identity checks |
| POST `login` | Email, prehash, CAPTCHA → session | Turnstile login action |
| POST `recover` | Email, new prehash, saved recovery code, CAPTCHA → rotated recovery/session | Turnstile recover action; old sessions revoked |
| GET `me` | Owner profile, CSRF, workspace revision/entries, counts and rewards | Session cookie |
| PUT `notes` | Revision and complete validated entries → next revision | Session, CSRF, atomic quota/revision checks |
| POST `logout` | Empty JSON → expired cookie | Session and CSRF |
| DELETE `me` | Current credential prehash → permanent application-data deletion | Session, CSRF and password proof |
| POST `verify/request` | Empty JSON → verification email requested | Session, CSRF, sender ready and send quotas |
| POST `verify/confirm` | Legacy single-use token → email confirmed | Same signed-in account, CSRF and token expiry |
| GET `rewards` | Current catalogue metadata, qualification and counts | Session; not plaintext scripts |
| GET/HEAD `sponsor/ID` | Current authorized file / bodyless server integrity check | Session and current qualified rewards |

`account_users` owns profile metadata; `account_credentials` owns only protected verification/recovery material, identity/referral code and consent. `account_sessions` owns expiring token hashes/CSRF. `account_workspaces` owns snapshot revision/write token; `account_notes` stores owned entries, and `account_notes_usage` stores total logical bytes. `account_daily_activity` counts unique dates, `account_referrals` links inviter/invitee, `account_signup_networks` stores expiring keyed network signals, `account_rate_limits` stores expiring hit buckets, and `account_email_tokens` stores expiring hashed single-use proofs. `account_limits` is the SQL policy singleton; `account_schema_migrations` is the application schema record. Do not attach private table exports to public bug reports. The reserved legacy `abuse_signals` table is not the active rate-limit implementation.

Portal fetches use `redirect: 'manual'` and reject every non-success response, including redirects. This preserves the fixed Test origin and avoids a workerd runtime failure observed with `redirect: 'error'`, despite that value appearing in the general Request documentation. The service fixture asserts manual mode and rejects a redirected upstream; live publication must still verify the actual Worker response.

## Shared account overlay and floating TXT

`assets/account-shell.js` and `account-shell.css` provide one account window for every website page and generated lesson. The existing navbar IDs `nav-home` / `merged-home` remain as compatibility hooks, but their icon, label and behavior are now Account. They open a dialog on the current page; they do not navigate away. `page-controls.js` provides a separate bordered Home link immediately left of Back on subpages. The homepage brand also remains a home link.

The window embeds only the configured secure Worker portal. Signed-out users choose Create account, Sign in or Reset password; forms remain closed until selected. Signed-in users get New TXT, Load TXT, New folder and Load folder actions. File pickers are activated by actual user clicks inside the secure frame, preserving browser user-activation requirements. Private files and credentials never pass to the surrounding website. The frame sends only a signed-in boolean or a float-window request, authenticated by its exact origin, source window and a random per-window bridge nonce. Floating mode uses a non-modal window so the underlying page stays usable. Close hides the same frame; the TXT button reopens it without destroying its in-memory draft. Full navigation can unload it, so existing unsaved-change warnings and exports still matter. Notes sync/export retain their prior revision and quota safeguards.

Embedded sessions use a separate `__Host-dedsec_embed` cookie: Secure, HttpOnly, SameSite=None, Partitioned and Path=/. `X-DedSec-Embedded: 1` selects this session; ordinary top-level sessions retain SameSite=Lax. Origin and CSRF checks remain mandatory, no cross-origin API access is enabled, and the Worker authorizes framing only by the selected profile's exact configured origin. Session partitions are distinct across sites. Older browsers that block embedded storage can use the explicit secure-portal fallback in a separate tab; this does not weaken authentication. See [MDN CHIPS](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies/Partitioned_cookies).

The separate Reset password tab selects the reset-by-recovery-code flow; the duplicate Forgot password shortcut was removed from Sign in. It works without email delivery, rotates the recovery code and revokes old sessions. A signed-in Change password form additionally requires the current password, a repeated new password and CSRF; POST `password` verifies the current prehash, creates a new password salt/verifier, rotates recovery, revokes sessions and issues a fresh session. Pending notes must sync before a client password change. Save the newly shown recovery code. There is no email-reset claim while the email provider is unconfigured.

## Explicit browser storage and transfers

Cloud is the default. `assets/account-local.js` provides IndexedDB database `dedsec-private-txt-v1`, object store `workspaces`. It stores a validated snapshot, monotonic revision and mode only after the user selects browser storage and confirms the warning. The key is SHA-256 of the build profile plus an opaque account ID returned only in authenticated `/me`; it contains no email, credentials or session tokens. A new account reusing a deleted email gets a different identifier. The identifier/hash is not encryption or a defence against someone controlling the browser profile. Parent website frames never receive it.

`account-live.js` routes the serialized save queue to D1 or IndexedDB. A readwrite transaction compares the expected local revision before replacing a snapshot, rejecting another tab’s stale writes. Errors retain the in-memory draft and warn to export. Sign-out first flushes the selected destination; the browser copy remains for the next sign-in. Account deletion removes server data and attempts local deletion on that browser; other browsers and exported backups are independent. Clearing cache/site data, eviction, browser-profile deletion or private browsing can lose local notes permanently. Persistent local notes do not make account authentication work offline. Browser storage can be denied, especially in older embedded browsers; use the separate-tab portal and TXT/ZIP export as fallback.

Switching to local first flushes cloud changes, then merges any retained browser copy and writes it durably before changing mode. Switching back saves the local draft, fetches the current cloud revision and calls pure `account-core.merge`. Identical files fold together and preserve either pin; case-insensitive path conflicts keep both contents with deterministic `(local N)` names. Folder mappings carry renamed parent paths to their descendants. The complete merged snapshot is validated against byte/file/folder/depth limits before confirmation and a single revision-checked PUT. D1 independently enforces global remaining space. No cloud deletion or local clearing precedes success. Failures/cancellation retain local mode. A retained browser copy remains after successful transfer until cleared; do not describe cloud selection as automatic erasure of local data. Public search indexes only the static explanatory account page, never IndexedDB/D1 contents.
