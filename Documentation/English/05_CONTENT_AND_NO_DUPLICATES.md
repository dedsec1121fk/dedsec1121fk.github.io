# Content architecture and duplicate prevention

## Canonical roles
`dedsec/Pages/`, `dedsec/el/Pages/` and `dedsec/Assistance/` are imported reference pages from the official DedSec website. The production website remains canonical for that material. Do not hand-edit copies in Test expecting those edits to survive an importer refresh. `data/en.js`, `data/el.js` and `data/methods.js` contain already-built learning records with full text; they allow standalone local search without fetching the private source repository.

The source of truth for the **original** learning materials remains Developer-Mind-Project until every source file has been explicitly copied and verified under `source/developer-mind/`. The website indexes are runtime snapshots, not a replacement for source Markdown, scripts, licensing or changelog.

## What counts as an unwanted duplicate
Two launcher icons leading to the same destination without a clearly different function are redundant. Two records sharing a stable `id` are invalid. A passage duplicated merely to inflate length adds no value; merge or cross-link it instead. English and Greek translations are **intentional parallel content**, not duplicates. Main DedSec articles and Developer Mind lessons may address related ideas but serve different purposes; do not delete one solely because keywords match.

The UI's `APPS` array maps `[English title, Greek title, pixel icon key, destination, kind]`. Keep unique route targets and full bilingual labels. DedSec reference links must remain before the archive links. An explicitly external Sponsor Us shortcut remains intentionally outbound.

## Adding a lesson
Update the canonical source Markdown first. Give each new item a unique ID and meaningful title, group and descriptive body; create a substantive Greek equivalent rather than word substitutions. Regenerate the two published JS arrays, inspect the ID sets, preserve code examples, run validator, then test search queries for terms and actual error messages in both languages.

## Removing content
Before removing a shortcut, verify that its feature remains discoverable elsewhere. Before removing a guide, search all links and related translations. Do not erase licenses, provenance, attribution, user-created work, or the original sources while Test is still a staging site.

### Duplicate overlay and safety rules
When two overlays target the same lesson, retain the complete, more substantive replacement instead of concatenating both. The cleanup tool applies an automated content heuristic; editors must still check important differences manually. It must not delete a canonical lesson ID or original executable `.py`/`.sh` source. Run `python3 scripts/audit_knowledge.py` to catch duplicate bodies, IDs, paths, locale mismatches and repeated source content, then `python3 scripts/audit_knowledge_depth.py` for effective-page parity and unresolved editorial debt.

### Testing and actual release readiness
A **successful Test website deployment is not editorial signoff**. The workflow also runs Python unit tests, language/website validation and Chromium mobile/desktop checks; its separate `--strict` editorial gate currently reports outstanding short lessons, boilerplate, empty sections and duplicated paragraphs. Never describe the entire knowledge corpus as complete while that gate says NOT READY. Improve targeted English/Greek counterparts with real syntax, testable inputs, expected behavior, failure analysis and explicitly stated runtime limits. Batch source changes, preserve the main branch, never modify production without separate authorization, and use the last actual GitHub Actions run for status.
