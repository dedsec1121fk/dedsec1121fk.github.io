# Επαναφορά έκδοσης χωρίς διαγραφή Git history

## Τι συμβαίνει
Μια έκδοση χρειάζεται ακριβές commit, επαληθευμένα tests, αλλαγμένα αρχεία και θέματα migration. Το GitHub Pages μπορεί να έχει νέα έκδοση ενώ το κινητό κρατά cached assets.

## Πρακτικός έλεγχος
Προτίμησε git revert για δημοσιευμένη προβληματική αλλαγή γιατί διατηρεί το ιστορικό. Απόφυγε πλήρη αντικατάσταση branch χωρίς έλεγχο.

## Συνήθεις παγίδες
Τεκμηρίωσε κριτήριο επαναφοράς πριν το deployment και ξαναέλεγξε links, γλώσσα, προσβασιμότητα και τοπικά δεδομένα μετά.

## Μικρό παράδειγμα για προσαρμογή
```text
git log --oneline -5
```

## Έλεγξε συμβατότητα δεδομένων πριν το code revert
Αν release B προσθέτει configuration field που το A δεν διαβάζει, επιστροφή του κώδικα στο A μπορεί να αφήσει persisted configuration του B. Το rollback plan πρέπει να δηλώνει readable data version, ύπαρξη migration backup και συμπεριφορά παλιάς εφαρμογής με το νέο field. Δοκίμασέ το πριν τη δημοσίευση και όχι στη διάρκεια διακοπής.

Κανονικό revert προσθέτει νέο commit με αντίστροφη αλλαγή. Το revert merge χρειάζεται explicit mainline-parent επιλογή, οπότε μην αντιγράφεις συνταγή ενός απλού commit χωρίς εξέταση ancestry. Έλεγξε τελικό tree και tests· το μήνυμα revert δεν αποδεικνύει επαναφορά λειτουργίας.

Κράτησε source commit, artifact hash, build configuration και deployment αποτέλεσμα. Στο κινητό ξεχώρισε deployed έκδοση από cached response μέσω asset URLs/headers και σκόπιμου reload. Επιτυχία workflow σημαίνει ότι πέρασαν τα συγκεκριμένα steps, όχι ότι δοκιμάστηκε κάθε πραγματική υποστηριζόμενη συσκευή.
